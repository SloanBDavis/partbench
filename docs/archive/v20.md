# V20 Release Record: Connected Local Agent Workflow

Status: **Complete (2026-07-31)**

Product V20 is unrelated to the existing `web-cad.project.v20` schema name,
which belongs to product V16. V20 introduces no project schema.

V20 connects the existing structured agent and MCP stack to the Partbench
project open in the browser. It adds no CAD feature family. Its value is making
every completed CADOps command and query useful in one live human-and-agent
workflow.

The release has exactly two approval modes:

- **Manual approval** (`manualApproval`) — the default. Agent commit requests
  become visible proposals and wait for explicit Approve or Reject.
- **Approve everything** (`approveAll`) — agent commit requests execute without
  another prompt. Agent-requested dry-runs remain dry-runs.

There is no third mode, per-tool policy, remembered exception, risk classifier,
or agent-controlled approval setting.

## Product Goal

After V20, a user must be able to:

1. start one local Partbench session that serves the production browser app and
   exposes the existing MCP stdio tools;
2. open or create a project in that browser and have MCP queries read that exact
   live project rather than a separate in-memory document;
3. let an agent inspect the current semantic selection;
4. use Manual approval to preview an agent commit, inspect its operations,
   semantic diff, warnings, and blockers, then approve or reject it;
5. use Approve everything to commit valid agent requests immediately;
6. see approved changes rebuild in the viewport, mark the project dirty, and
   appear in history with agent and MCP audit metadata;
7. undo an approved agent transaction through the existing undo path; and
8. save and reopen the result through the existing `.wcad` workflow.

V20 completes the local AI-native product loop. It does not embed an LLM or
interpret natural language.

## Why V20 Comes Now

V1-V19 already provide a broad typed command/query surface, dry-run responses,
semantic diffs, actor/audit metadata, undo/redo, stable references, exact
geometry, and project storage. The current MCP stdio process nevertheless owns
its own `CadEngine`; restarting it loses that document, and moving work into the
browser requires a manual JSON handoff.

Adding more commands before connecting the two product surfaces increases the
eventual first-pass bridge and approval matrix. V20 freezes the bridge while the
authority model is still simple: one local process, one connected browser tab,
one authoritative project, and one pending proposal.

## Non-Negotiable Architecture

1. The `CadEngine` already used by `apps/web` remains the only live document
   authority. The launcher and MCP process never keep a synchronized project
   copy.
2. Every agent mutation still executes through CADOps. Approval grants
   permission to attempt a command; it never bypasses command validation.
3. Human and agent commits share the existing `AsyncCadCommandExecutor` queue so
   they cannot race or allocate IDs from different snapshots.
4. MCP remains an adapter over the agent adapter and CADOps. The local relay does
   not define CAD behavior.
5. Renderer state, meshes, exact metadata, selection, approval state, proposals,
   tokens, and connection state remain derived or session-only.
6. V12-V19 commandability, topology, storage, UI, performance, and adapter
   matrices remain compatibility requirements.
7. V20 adds no production dependency by default and no new workspace package.

The live path is:

```text
MCP client
  -> existing line-delimited stdio server
    -> existing MCP adapter
      -> authenticated local browser relay
        -> live agent adapter port
          -> shared AsyncCadCommandExecutor / CadEngine
            -> CADOps document mutation or query
```

## Binding Decisions

### 1. Reuse the current stdio package as the launcher

`packages/mcp-stdio-server` becomes the local product entrypoint. Its executable
does three jobs and no more:

1. bind an HTTP server to an operating-system-selected port on `127.0.0.1`;
2. serve the existing production `apps/web` bundle with the required WASM,
   COOP, COEP, and CORP headers; and
3. relay MCP adapter requests and responses to the connected browser session.

It opens the generated local URL in the default browser using Node standard
library process APIs. It does not add a Rust/Go launcher, Electron, a second web
app, or a new package.

The public MCP transport remains stdio. The browser relay is private local
plumbing, not a new Streamable HTTP MCP endpoint.

### 2. Use one small request/response relay

The browser uses same-origin `fetch` long-polling against the launcher: one
endpoint receives the next adapter request and one returns its response. Node's
standard `http`, `crypto`, `fs`, `path`, and `child_process` modules are enough.

Only one browser tab may own a session. A second tab receives a structured
`AGENT_SESSION_ALREADY_CONNECTED` error and never observes or mutates the
project.

`tools/list` remains available from the Node-side MCP adapter. Tool calls wait
for the browser connection and fail cleanly if the session disconnects.

### 3. Keep the MCP adapter out of the web bundle

`CadMcpServer` gains one narrow awaitable execution port with four operations:

- execute an agent batch request;
- execute an agent query request;
- inspect the existing V8 project surface; and
- read the current semantic selection.

The current in-memory adapter remains the default implementation for existing
tests and programmatic callers; its selection is `none`. The connected
implementation relays those four typed calls to the browser. The browser
lazy-loads only the agent adapter
bridge after a local session connects; the MCP tool registry and JSON-RPC
handler remain in Node.

This is not a generic RPC framework. No arbitrary method registration, plugin
transport, retry policy object, or transport factory is added.

### 4. The browser executes against the current project

The browser-side adapter uses the same `CadEngine` and
`AsyncCadCommandExecutor` as human UI actions. After an accepted agent commit,
the app uses its existing document publication path to:

- publish the new document snapshot;
- reconcile selection;
- refresh derived geometry and exact metadata;
- mark the current project file dirty; and
- refresh transaction history.

An agent commit is one normal CADOps transaction. V20 adds no shadow history,
agent branch, merge step, or second undo stack.

### 5. Manual approval is one pending commit proposal

In `manualApproval`, an incoming `cad.batch` with `mode: "commit"` is handled as
follows:

1. capture the current canonical project source identity;
2. execute the same operations as a CADOps dry-run;
3. if the dry-run fails, return that failure immediately and create no proposal;
4. if it succeeds, show one proposal containing the operation summaries,
   semantic diff, warnings, blockers, actor, audit metadata, and source
   identity;
5. keep the MCP tool call pending while the user chooses Approve or Reject;
6. on Approve, require the current source identity to equal the previewed
   identity, then submit the original commit through the shared command queue;
7. on Reject, return a structured rejection and change no project source.

Only one commit proposal may be pending. Another commit request receives
`AGENT_APPROVAL_BUSY`. Read-only queries and caller-requested dry-runs remain
available while a proposal is pending.

Human edits are not locked. If project source changes before approval, the
proposal becomes stale, Approve is disabled, and the pending call returns
`AGENT_PROPOSAL_STALE`. The agent must dry-run again.

### 6. Approve everything is immediate permission, not weaker validation

In `approveAll`, a valid `cad.batch` with `mode: "commit"` enters the shared
command queue immediately. CADOps validation, structured errors, semantic
diffs, actor/audit metadata, geometry rebuild, dirty state, history, and undo
behavior are identical to a manually approved commit.

`approveAll` does not:

- convert `dryRun` requests into commits;
- allow filesystem paths, browser handles, OPFS paths, shell commands, network
  access, or arbitrary scripts;
- bypass unsupported CAD rows or stale-reference checks; or
- approve work after the local session ends.

### 7. The human owns the approval mode

The approval mode is changed only from the Partbench UI. New sessions start in
`manualApproval`. Selecting Approve everything requires one explicit human
confirmation for the current session.

Approval mode is browser-session/UI state. It is absent from CADOps, project
JSON, `.wcad`, history, source identity, OPFS, and browser preference storage.
Reload, disconnect, or launcher restart returns to Manual approval.

The existing MCP `allowCommit` argument remains accepted for compatibility but
its value is ignored in a connected V20 session: `true`, `false`, or omitted
all follow the same browser-selected mode. The mode, or the explicit approval
of one pending proposal, supplies the effective commit permission. The existing
in-memory adapter keeps its current `allowCommit` behavior for compatibility.

Mode controls are disabled while a proposal is pending; the user must Approve
or Reject first. V20 adds no Approve once mode, per-tool grants, remembered
allowlists, timers, role matrix, or risk-based prompting.

### 8. Expose the current primary semantic selection read-only

V20 adds `cad.get_selection`. It returns the browser's current primary semantic
selection plus the current project source identity. The bounded response union
is:

```ts
type CadCurrentSelection =
  | { kind: "none" }
  | { kind: "sketch"; sketchId: string }
  | { kind: "sketchEntity"; sketchId: string; entityId: string }
  | { kind: "object"; objectId: string }
  | { kind: "body"; bodyId: string }
  | {
      kind: "generatedReference";
      bodyId: string;
      stableId: string;
      expectedKind?: "body" | "face" | "edge" | "vertex";
    }
  | { kind: "namedReference"; name: string };
```

When current UI state overlaps, the single returned selection uses this
precedence: named reference, generated reference, sketch entity, sketch, body,
object, then none. V20 does not invent durable parameter, feature, origin-plane,
region, or multi-selection state merely to expose it to agents.

The response contains semantic IDs only. It excludes hover, pixels, renderer
IDs, selection-buffer IDs, region-candidate keys, provisional editor choices,
and measurement overlay state.

V20 does not add `cad.set_selection`, screenshots, or render-view tools.

### 9. Add one restrained Agent page to Project

The existing Project workspace gains an **Agent** page, reachable through the
existing navigation and command search. It shows:

- Connected or Disconnected status;
- exactly two approval-mode choices;
- one pending proposal with operation labels, semantic diff summary, warnings,
  blockers, and technical details; and
- Approve and Reject actions in Manual approval.

It is not a chat panel. It does not display chain-of-thought, accept natural
language, manage model providers, or duplicate History. After commit, the
existing History page remains the audit record and the existing Undo action
remains the rollback path.

The page follows the V18 action ownership, Apply/Cancel, keyboard, focus,
responsive, accessibility, and visual-token contracts. Approval mode and
proposal actions have one owner and are not duplicated in the ribbon or
viewport.

### 10. Connection and approval failures are explicit

V20 adds this small adapter/session diagnostic set:

```text
AGENT_SESSION_NOT_CONNECTED
AGENT_SESSION_ALREADY_CONNECTED
AGENT_SESSION_TOKEN_INVALID
AGENT_SESSION_DISCONNECTED
AGENT_APPROVAL_BUSY
AGENT_COMMIT_REJECTED
AGENT_PROPOSAL_STALE
```

Malformed JSON-RPC, unknown tools, invalid tool arguments, command validation,
and permission failures keep their existing error paths. V20 does not create a
second error taxonomy for them.

Project replacement, New, Open, browser reload, or session disconnect rejects
and clears a pending proposal. A failed or rejected proposal never enters
history or changes the dirty state.

### 11. Local security is release scope

The launcher must:

- bind only to `127.0.0.1` on a random port;
- generate a cryptographically random 256-bit session token;
- put the token in the opened URL fragment so it is not sent in ordinary asset
  requests or referrers;
- require that token on every relay request;
- validate same-origin requests and the expected loopback host;
- serve only the fixed production bundle with path traversal blocked;
- set the existing cross-origin isolation and correct WASM MIME headers; and
- close pending MCP calls when the browser or stdio process disconnects.

The server exposes no project-file path, directory listing, general HTTP file
API, command execution endpoint, network bind option, or hosted authentication
claim.

### 12. V20 requires no project migration

V20 adds no authoritative project source. Current exports continue to use the
lowest sufficient schema through `web-cad.project.v22`; `.wcad` remains
`partbench.wcad.v2`.

The following remain session-only and must never affect canonical project
bytes or source identity:

- session token and port;
- approval mode;
- pending proposal and preview response;
- current semantic selection; and
- relay request IDs and connection status.

Agent commits contain only their ordinary CADOps operation, semantic diff,
actor, and audit records. Existing history serialization already owns those
records.

## Approval Matrix

| Request                              | Manual approval                      | Approve everything              |
| ------------------------------------ | ------------------------------------ | ------------------------------- |
| Query                                | Execute immediately                  | Execute immediately             |
| `cad.batch` dry-run                  | Execute without proposal             | Execute without proposal        |
| Invalid commit                       | Return validation failure            | Return validation failure       |
| Valid commit                         | Show one proposal; Approve or Reject | Commit immediately              |
| Commit while one proposal is pending | `AGENT_APPROVAL_BUSY`                | Not applicable                  |
| Commit after source changed          | `AGENT_PROPOSAL_STALE`               | Validate against current source |

This table is complete. A later release must explicitly amend V20 to add
another approval behavior.

## Implementation Slices and Gates

### Slice A — Contracts and async adapter seam

- freeze the two approval-mode values, selection response, proposal shape, and
  diagnostic codes;
- give `CadMcpServer` the narrow awaitable adapter port;
- preserve existing in-memory adapter behavior and tool schemas; and
- make stdio request handling await tool results by request ID without letting
  one approval-waiting call block `tools/list`, queries, dry-runs, or a busy
  response to another commit.

**Gate A:** existing agent/MCP/stdio tests pass unchanged except for intentional
async call sites; focused tests prove out-of-order async completion preserves
the correct JSON-RPC IDs and that the new types reject extra mode values and
malformed selection/session data.

### Slice B — Local launcher and authenticated relay

- serve the built app from the existing stdio package;
- open the loopback URL and connect exactly one authenticated browser tab;
- relay adapter calls without document ownership; and
- implement disconnect and security diagnostics.

**Gate B:** a real browser connects, an invalid token/origin/host/path fails,
the second tab is refused, and no launcher code can read or write an arbitrary
user path.

### Slice C — Live project execution and selection

- connect the browser adapter to the current engine and shared command queue;
- publish committed documents through the existing app synchronization path;
- expose `cad.get_selection`; and
- prove query, dry-run, commit, dirty state, derived rebuild, history, undo, and
  `.wcad` round-trip against the same project.

**Gate C:** the stdio client and browser report the same source identity before
and after every operation; no second `CadEngine` exists in the connected path.

### Slice D — The two approval modes and Agent page

- add the Project Agent page;
- implement Manual approval proposal/reject/approve/stale behavior;
- implement Approve everything and its session-only confirmation;
- preserve read/dry-run availability while a proposal is pending; and
- complete keyboard, focus, responsive, accessibility, and history audit paths.

**Gate D:** every row in the Approval Matrix passes in browser integration, and
no third mode or hidden permission path exists.

### Slice E — Release proof and documentation

- run compatibility, bundle, performance, security, and browser audits;
- reconcile README, architecture, implementation plan, native format, AGENTS,
  and package documentation; and
- record measured evidence without expanding scope.

**Gate E:** every Must item and named workflow passes, the non-goal audit finds
no partial surface, and V12-V19 release matrices remain unchanged.

Slices are sequential because each changes a shared transport or browser
authority boundary. Implementation should not create a parallel PR stack for
these files.

## Normative Release Workflows

V20 adds three named release commands:

```sh
pnpm smoke:v20-live-agent-workflow
pnpm smoke:v20-local-security
pnpm check:v20-bundle
```

`smoke:v20-live-agent-workflow` must use the production web build, a real
Chromium-compatible browser, the real stdio JSON-RPC process, and the existing
CADOps engine. It proves:

1. MCP reads a browser-opened project and its semantic selection;
2. Manual approval previews one parameter or feature edit, Reject leaves source
   identity unchanged, Approve commits it, viewport/history update, and Undo
   restores the prior model state; the canonical project identity advances
   because transaction/redo history is authoritative source;
3. a human edit makes a pending proposal stale;
4. Approve everything commits two valid requests without prompts while an
   explicit dry-run remains non-mutating; and
5. Save/Open `.wcad` preserves approved source and agent audit history.

`smoke:v20-local-security` proves loopback-only binding, random-token rejection,
origin/host checks, second-tab rejection, path traversal rejection, no
filesystem/tool boundary regression, and pending-call cleanup on disconnect.

`check:v20-bundle` retains the V19 critical UI, CSS, worker, and OCCT WASM caps.
The lazily connected agent bridge must fit inside the existing all-UI cap; a cap
increase requires a separate approved plan amendment.

Full release validation also runs:


## Must Definition of Done

V20 is complete only when:

1. The production stdio entrypoint launches and serves the production browser
   app from loopback without a new package or production dependency.
2. Connected MCP tools operate on the browser's current authoritative project,
   not an in-memory replica or JSON-synchronized copy.
3. Human and agent commits share one command queue and retain all CADOps
   validation, semantic diff, audit, history, rebuild, and undo behavior.
4. Manual approval and Approve everything are the only approval modes, Manual
   is the default, and only the human UI can change mode.
5. Every Approval Matrix row has focused and browser integration proof.
6. Manual proposals bind to source identity, reject stale approval, and never
   mutate source before Approve.
7. `cad.get_selection` returns only the documented semantic selection union and
   never leaks renderer, pixel, mesh, or derived candidate authority.
8. Approved commits update the viewport, dirty state, history, and `.wcad`
   round-trip; rejected/failed/stale proposals update none of them.
9. The local security requirements and structured disconnect behavior pass in
   the production entrypoint.
10. V20 adds no project schema, package version, CAD operation, geometry recipe,
    renderer contract, hosted service, or arbitrary file capability.
11. Existing V12-V19 tests and named V19 compatibility workflows pass.
12. All three named V20 commands and full release validation pass.
13. README, architecture, implementation plan, native format, AGENTS, package
    docs, and this plan describe the same completed behavior at release.
14. No V20 non-goal is partially exposed as a supported product path.

## Explicit Non-Goals

- A built-in chatbot, prompt box, model provider, natural-language parser, or
  chain-of-thought display.
- More than the two approval modes, including Approve once, per-tool rules,
  remembered allowlists, time windows, roles, or risk scoring.
- An agent-settable approval mode or caller permission that bypasses the UI.
- Multiple browser authorities, multiple live projects, collaboration, merging,
  branches, or durable proposals.
- Streamable HTTP MCP, WebSocket infrastructure, hosted MCP, remote binding,
  accounts, cloud projects, or production hosted auth.
- Agent filesystem paths, file handles, OPFS paths, automatic Save, arbitrary
  imports/exports, scripts, shell commands, or network access.
- `cad.set_selection`, screenshots, render-view tools, camera control, hover,
  or renderer/selection-buffer exposure.
- New CAD commands, queries other than `cad.get_selection`, feature families,
  topology rows, exact geometry recipes, assemblies, drawings, or WebGPU.
- A new document schema, `.wcad` version, persisted session state, or new
  package entry.
- A new workspace package or production dependency without an explicit plan
  amendment.

V20 has no Stretch section. Additional surfaces belong in a later release.

## Simplification Review Record

The plan received three required deletion passes before implementation:

1. **Scope deletion:** removed built-in chat, natural-language parsing,
   screenshots, render control, selection mutation, agent file writes, hosted
   MCP, new CAD capability, a redundant agent-identity display, and synthetic
   parameter/feature/origin/region selection states. Only live project access,
   the current primary semantic selection, approval, commit, history, undo, and
   save remain.
2. **Architecture deletion:** reused `packages/mcp-stdio-server`, the existing
   web app, MCP/agent adapters, `AsyncCadCommandExecutor`, `CadEngine`, Project
   workspace, History, Undo, and `.wcad`. Removed a new launcher package, a
   second engine, project synchronization, WebSocket dependency, generic RPC
   framework, unspecified selection side channel, and separate agent history.
3. **Policy deletion:** reduced approval to `manualApproval` and `approveAll`.
   Removed caller authority, Approve once, per-tool grants, remembered choices,
   expiry timers, roles, risk scoring, and durable proposals.

End of the completed V20 release record. Later work must stop at this boundary
unless an explicitly approved milestone amends it.
