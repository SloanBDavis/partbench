# V21 Plan: Production Single-Part Reliability and Exact Interchange

Status: **Approved for implementation (2026-08-01). Slices A-B are complete; Slice C is next.**

Product V21 is unrelated to the existing `web-cad.project.v21` schema name,
which belongs to product V17. V21 adds no authoritative project source, so
current projects continue to use the lowest sufficient schema through
`web-cad.project.v22`; `.wcad` remains `partbench.wcad.v2`.

V21 is the single-part completion release before assemblies. It does not add a
new sketch entity, feature family, modeling support row, assembly concept, or
file format. It makes every already-supported active Partbench body participate
in one trustworthy exact-result pipeline from rebuild through STEP output.

The release center is:

```text
completed V12-V19 source and command matrices
-> one current exact-body resolver
-> one identity-bound derived B-rep artifact
-> display / topology / metadata / mass / selection / measurement agreement
-> selected-body or multi-body named AP242 STEP output
-> save/open/rebuild/export/re-import proof
```

There is no Stretch section. Every outcome and support row in this document is
Must unless it is explicitly labeled a non-goal.

## Product Goal

After V21, the following statement must be true:

> If Partbench can create a body through a completed supported command path,
> that active body can be rebuilt, displayed, inspected, measured, saved,
> exported as exact STEP, re-imported, and verified without encountering a
> feature-specific export dead end.

A user must be able to:

1. build any active body covered by the completed V12-V19 support matrices;
2. see one truthful current/blocked/pending/failed state for that body across
   the viewport, Project, Inspect, topology, measurement, and export surfaces;
3. export one explicitly selected active body or an explicit ordered set of
   active bodies;
4. export every active healthy body in a project without silent omission;
5. retain document units and body names in an AP242 STEP artifact;
6. export a standalone imported STEP body and every downstream imported-body
   result already accepted by the completed command matrices;
7. edit source while an export is running and receive a stale-result rejection
   rather than a download for the old model;
8. cancel or retry export without changing project source, history, dirty
   state, checkpoints, selection, or approval state;
9. save and reopen through `.wcad`, rebuild exact results, export again, and
   obtain geometrically equivalent output; and
10. ask through the existing agent/MCP query surfaces which bodies are ready
    and why, without granting agents file bytes or file-writing authority.

## Why V21 Comes Before Assemblies

Assemblies multiply part-level behavior across definitions and instances. The
current code already has a broad single-part feature set, but exact output is
still reconstructed by a narrower export-only union. That leaves completed
hole, chamfer, fillet, shell, pattern, mirror, loft, imported-body, and other
result paths unable to share the exact path already used by metadata and
checkpoint generation.

V21 closes that architectural split first. Assemblies can then consume one
exact part artifact contract instead of inheriting per-feature export special
cases.

## Non-Negotiable Architecture

1. The authoritative `CadDocument` and transaction history remain the source
   of truth. B-rep artifacts, topology snapshots, metadata, meshes, STEP bytes,
   readiness projections, and export jobs remain derived or session-only.
2. Cad-core decides which bodies exist, which are active, which completed
   modeling matrix applies, and whether source/dependency/reference state is
   valid. React, the renderer, geometry-worker, and OCCT do not expand command
   eligibility.
3. `apps/web` resolves current app-owned inputs such as checkpoint bytes and
   current derived evidence. Cad-core never receives browser file handles,
   OPFS paths, raw OCCT handles, renderer IDs, or export bytes.
4. Geometry construction remains isolated behind geometry-kernel,
   geometry-worker, and occt-wasm. Cad-core never calls OCCT.
5. One exact-body source resolver and one OCCT exact-shape builder serve exact
   metadata, topology/checkpoints, artifact generation, and STEP export. V21
   must remove the production dependency on the narrower export-only geometry
   recipe mapper.
6. Display meshes remain derived views. A mesh cannot make a body exact-ready,
   and a displayed stale mesh cannot authorize export.
7. Every export plan binds to canonical project source identity and every body
   entry binds to current body source identity. Both are checked before exact
   work and again before download.
8. STEP output reads validated derived exact B-rep artifacts. The STEP writer
   does not rebuild features, infer sketch intent, or choose alternative source
   geometry.
9. Existing V12-V20 command, topology, UI, storage, performance, and agent
   behavior remains compatibility scope. V21 may complete a missing derived
   result path but may not broaden a modeling support matrix silently.
10. V21 adds no production dependency, workspace package, second geometry
    engine, background service, or new authority path.

## Binding Decisions

### 1. V21 Completes Existing Bodies; It Does Not Add Modeling Breadth

The universal V21 rule is:

```text
active body
+ source command accepted by a completed V12-V19 support row
+ current dependency/reference/rebuild state is healthy
+ required checkpoint payload is present and valid where applicable
= exact artifact buildable and STEP exportable
```

Unsupported combinations remain unsupported. Examples include recursive
pattern seeds beyond the completed V16 matrix, unsupported sweep/loft profiles,
unproven edge-finish targets, arbitrary-result topology commandability, and
unsupported imported-body downstream targets. V21 must not make one of those
commands legal merely because the internal B-rep builder could execute it.

Conversely, a completed command row may not remain `deferred` only because the
old export mapper lacks that feature kind. That is the defect V21 closes.

### 2. Use One Canonical Current Exact-Body Resolver

The current app already creates `DerivedExactMetadataSource` values for most
active authored bodies and uses `OcctExactBodyMetadataSource` to build exact
OCCT shapes for extrude/boolean, revolve, sweep, loft, pattern, mirror, shell,
imported B-rep, hole, and edge-finish sources.

V21 promotes that path into the canonical current exact-body resolver. The
resolver accepts the current document, completed support policy, public
topology/reference evidence, and app-owned checkpoint payloads. It returns
exactly one of:

```ts
type CurrentExactBodyResolution =
  | {
      readonly status: "ready";
      readonly bodyId: BodyId;
      readonly sourceType: CadBodySource["type"];
      readonly sourceIdentitySignature: string;
      readonly cacheKey: string;
      readonly source: ExactBodyMetadataSource;
    }
  | {
      readonly status:
        | "pending"
        | "stale"
        | "blocked"
        | "failed"
        | "unsupported";
      readonly bodyId: BodyId;
      readonly sourceType: CadBodySource["type"];
      readonly diagnostics: readonly CadExactResultDiagnostic[];
    };
```

The exact type names may follow existing package conventions, but the union and
its semantics are binding.

The resolver must be exhaustive over `CadBodySource["type"]`. A compile-time
`satisfies` map and a runtime matrix test fail whenever a future body source is
added without an exact-result policy.

Primitive scene-object bodies join this resolver. They remain compatibility
source, but box, cylinder, sphere, cone, and torus already have exact OCCT
builders and may not remain an unexplained export hole.

### 3. Cad-Core Returns an Export Plan, Not Geometry or File Bytes

`project.exportReadiness` and `project.exportExact` remain the public query
entrypoints. V21 extends their response additively with a current export plan:

```ts
interface CadExactExportPlan {
  readonly format: "step";
  readonly schema: "AP242DIS";
  readonly units: DocumentUnits;
  readonly sourceIdentity: WcadSourceIdentity;
  readonly orderedBodyIds: readonly BodyId[];
  readonly allOrNothing: true;
  readonly planIdentity: string;
  readonly bodies: readonly CadExactExportPlanBody[];
}

interface CadExactExportPlanBody {
  readonly bodyId: BodyId;
  readonly bodyName: string;
  readonly partId: PartId;
  readonly featureId: FeatureId;
  readonly sourceType: CadBodySource["type"];
  readonly sourceIdentitySignature: string;
  readonly status: "ready" | "blocked";
  readonly diagnostics: readonly CadExportDiagnostic[];
}
```

Cad-core derives this plan from authoritative source and validated read-only
exact evidence. It does not return B-rep bytes, OCCT handles, worker cache keys,
or renderer data.

The existing `exportSources` and optional protocol artifact fields remain
readable for compatibility, but the production V21 browser path no longer uses
them. They are deprecated compatibility shapes, not the V21 execution
authority. Historical commands, diffs, JSON, CBOR, and `.wcad` never contain an
export plan or artifact.

### 4. Exact Artifacts Are Derived, Identity-Bound, and Session-Only

V21 adds an internal geometry-kernel/worker artifact contract:

```ts
interface ExactBodyArtifact {
  readonly bodyId: BodyId;
  readonly sourceKind: ExactBodyMetadataSource["kind"];
  readonly documentSourceIdentity: WcadSourceIdentity;
  readonly bodySourceIdentitySignature: string;
  readonly sourceCacheKeySha256: string;
  readonly brepFormat: "occt-brep";
  readonly brepWriter: "BRepTools.Write_3";
  readonly brepByteLength: number;
  readonly brepSha256: string;
  readonly brepBytes: Uint8Array;
  readonly metadata: GeometryKernelExactBodyMetadata;
  readonly topologySnapshot: GeometryKernelExactTopologySnapshot;
}
```

The exact field placement may be split between request metadata and artifact
payload to avoid duplicating public types. The following invariants are
mandatory:

- the B-rep bytes, metadata, topology snapshot, topology signature, and
  generated-reference evidence come from the same OCCT shape lifetime;
- `brepByteLength` equals the transferred byte length;
- `brepSha256` and `sourceCacheKeySha256` use the existing SHA-256 facilities;
- no artifact is source authority or part of canonical source identity;
- no artifact is written into project JSON, canonical CBOR, transaction
  history, redo, `.wcad`, or a topology source record automatically;
- an artifact may be retained only in bounded session memory for the current
  export/checkpoint operation and must be released after completion,
  cancellation, staleness, failure, or runtime disposal; and
- V21 does not add an OPFS exact-artifact cache. Rebuild first; persist only if
  a later measured release explicitly needs it.

### 5. Build the Artifact Through the Existing Exact Shape Boundary

`withOcctExactBodyShape` (or a directly equivalent shared helper) remains the
only feature-to-`TopoDS_Shape` dispatch used by metadata, topology, checkpoint,
artifact, and export work.

The artifact builder must:

1. validate the exact source before allocating OCCT builders;
2. construct one non-null shape through the completed source matrix;
3. compute metadata, topology, topology signature, and generated references;
4. serialize the same shape with `BRepTools.Write_3`;
5. release every OCCT object and temporary virtual file in success and failure;
6. return transferables without retaining detached buffers accidentally; and
7. return structured errors for missing bindings, invalid sources, empty/null
   shapes, topology limits, B-rep write failure, and resource limits.

The existing exact checkpoint builder must be refactored to consume this shared
artifact result rather than maintaining a second B-rep serialization path.
Explicit topology checkpoint commands and `.wcad` persistence keep their
existing authority and semantics.

### 6. Checkpoint-Backed B-Rep Is a Valid Internal Exact Leaf

A verified imported-body or topology-checkpoint B-rep may be an internal leaf
for exact reconstruction. It is accepted only when:

- the checkpoint source record exists and is active;
- payload manifest/body/feature IDs match source;
- byte length and SHA-256 match manifest evidence;
- the B-rep parses to a non-null shape;
- its topology signature matches the source/checkpoint identity required by
  the completed command path; and
- cad-core already considers the body/target/edge commandable under V12-V19.

This leaf closes exact-result gaps for standalone imported bodies and supported
downstream imported-body add/cut/hole/edge-finish results. It must not bypass
anchor promotion, command readiness, repair, or completed support matrices.

| Region extrude `newBody` | Must | Retained | Retained | Must |
| Supported extrude add/cut chain, including region tools | Must | Must | Must | Must |
| Supported topology-backed/result-body extrude add/cut | Must | Must | Must | Must |
| Entity/wire/region revolve in its completed mode matrix | Must | Must | Must | Must |
| Line, arc, or G1 line/arc-chain sweep in the V17 matrix | Must | Must | Must | Must |
| Parallel separated supported loft | Must | Must | Must | Must |
| Supported blind/through hole | Must | Must | Must | Must |
| Supported chamfer | Must | Must | Must | Must |
| Supported fillet | Must | Must | Must | Must |
| Linear pattern with completed V16 seed matrix | Must | Must | Must | Must |
| Circular pattern with completed V16 seed matrix | Must | Must | Must | Must |

V21 closes any current missing parity in that cell. The detailed geometry,
profile, topology, target, and seed submatrices remain exactly those in
`docs/v12.md` through `docs/v19.md`.

### 8. Selected and Multi-Body Export Is Explicit and All-or-Nothing

`project.exportExact.bodyIds` remains the explicit ordered body selection.

- An omitted or empty `bodyIds` selects all active bodies in canonical project
  body order.
- An explicit list preserves caller order.
- Duplicate IDs, missing IDs, consumed IDs, and IDs outside the current
  project are blocking validation errors.
- If any selected body is pending, stale, failed, unsupported, or blocked, the
  export produces no STEP bytes.
- Export-all never silently skips a blocked active body. The UI may offer the
  user an explicit supported subset, but that creates a new explicit plan and
  does not reinterpret Export all.
- A selected subset may export while an unrelated body is blocked.
- Exactly one plan becomes exactly one STEP artifact.

The plan identity is deterministic over format, schema, units, canonical source
identity, ordered body IDs, body names, body source identity signatures, and
the all-or-nothing policy.

### 9. STEP Output Is Named AP242 With Exact Units

The only V21 exact file format is STEP using schema `AP242DIS` and
`STEPControl_AsIs` shape transfer.

For every selected body:

- the STEP product name is the trimmed authored body name when present;
- otherwise the deterministic fallback is the current body ID;
- duplicate user names remain duplicate user names rather than being silently
  rewritten;
- Unicode names must round-trip through the supported OCCT/XDE name path;
- the document's `mm`, `cm`, `m`, or `in` unit is written explicitly; and
- coordinates and exact properties retain their physical scale.

The current minimal writer does not prove per-body product names. Slice A must
probe the required XDE/STEPCAF or equivalent bindings in the real browser
WASM. If missing, V21 adds only the required bindings inside the existing
`packages/occt-wasm` boundary. Body names may not be dropped, replaced with a
placeholder, or demoted from Must.

The writer capability response distinguishes basic STEP transfer from required
V21 named-product transfer. The production download action is unavailable
until both are available.

### 10. STEP Writing Consumes B-Rep Artifacts, Not Feature Recipes

The V21 writer input is conceptually:

```ts
interface ExactStepArtifactBodyInput {
  readonly bodyId: BodyId;
  readonly bodyName: string;
  readonly brepFormat: "occt-brep";
  readonly brepByteLength: number;
  readonly brepSha256: string;
  readonly brepBytes: Uint8Array;
}
```

The worker validates every artifact, reads each B-rep into a non-null shape,
attaches the product name, transfers shapes in plan order, sets AP242 and units,
writes once, validates non-empty bytes, and returns the artifact bytes as a
transferable.

The writer does not accept sketch profiles, feature parameters, topology
anchors, mesh buffers, or OCCT handles. The existing export-only
extrude/revolve/sweep source construction remains only as deprecated
compatibility code until callers are migrated; production V21 execution does
not use it.

### 11. Source Identity Is Checked Before and After Exact Work

The production export sequence is:

1. capture canonical project source identity;
2. ask cad-core for an exact export plan;
3. resolve every plan body through the current exact-body resolver;
4. require each resolved body identity to match the plan;
5. build exact artifacts under one cancellable user export generation;
6. verify artifact body identity, byte length, and hash;
7. write the named STEP artifact;
8. re-read canonical project source identity and selected body source
   identities; and
9. download only if every identity still matches.

Any human command, approved agent command, undo, redo, New, Open, JSON import,
`.wcad` replacement, topology repair, or source replacement that changes one
of those identities makes the result stale. The old bytes are discarded and
the user receives `EXPORT_SOURCE_CHANGED` or the final approved diagnostic
name. A stale export never downloads automatically after a retry.

History-only canonical identity changes may conservatively stale an export.
V21 prefers a harmless retry over delivering bytes whose audit context no
longer matches the open project.

### 12. One Current Exact-Result Projection Drives Product Status

V21 adds one pure app projection over:

- authoritative project/body lifecycle and dependency health;
- current display source and cache identity;
- current exact metadata source and cache identity;
- topology/body source identity;
- explicit checkpoint payload health where required; and
- any active export artifact/job identity.

It returns the same bounded state vocabulary for every consumer:

```ts
type CadCurrentExactResultStatus =
  | "pending"
  | "ready"
  | "stale"
  | "blocked"
  | "failed"
  | "unsupported";
```

The states have one deterministic meaning and precedence:

| Status | Meaning |
| --- | --- |
| `unsupported` | Cad-core's completed support policy has no legal row for this source/consumer combination. Successful geometry execution cannot change it. |
| `blocked` | The row is supported, but authoritative lifecycle, dependency, reference, checkpoint, selection, or resource evidence proves the current operation cannot proceed. |
| `failed` | The source is eligible and current, but its latest required derived build attempt ended in a structured error. |
| `pending` | The source is eligible and unblocked, and a required current derived result is absent or actively rebuilding. A stale prior mesh/result may remain visible only as explicitly stale, never current. |
| `stale` | No current build is active and derived evidence exists only for a different source identity. |
| `ready` | Every required source and derived evidence item exists and matches the current body identity. |

Support-policy and authoritative blockers are evaluated before derived state.
For otherwise eligible bodies, an active current build reports `pending`; its
terminal result becomes `ready` or `failed`. `stale` is used only when no
current build is active. Consumed bodies retain their lifecycle classification
and are never upgraded by a derived status.

`project.health`, `project.exportReadiness`, `project.exportExact`, body
topology, body mass properties, Project/File, Inspect, the status bar, and the
connected agent projection must consume that shared evidence or a direct
cad-core projection of it. They may phrase messages differently, but they may
not disagree about whether the same body is current and exact-ready.

The project-health response becomes exhaustive over primitive, extrude,
revolve, hole, chamfer, fillet, sweep, loft, pattern, mirror, shell, and
imported-body families. Additive fields preserve existing response members.

### 13. Display, Selection, and Measurement Agreement Is Body-Scoped

V21 does not expand the completed subentity selection support matrix. It does
require:

- an active exact-ready body never displays a stale prior mesh as current;
- a display failure cannot be reported as exact-export success without a
  diagnostic explaining that display is the failed derived consumer;
- body selection and Inspect show the same body lifecycle/exact status as
  Project/File;
- `body.massProperties`, project extents, and body-level exact measurements use
  matching current exact metadata from the artifact source identity;
- existing generated-reference and topology-anchor measurements retain their
  completed exact/source-semantic rules; and
- selected-body export resolves the semantic body ID, never a renderer ID,
  mesh ID, viewport pixel, or selection-buffer value.

Exact face/edge/vertex highlight architecture, generated vertex picking,
selection-buffer replacement, persisted measurement annotations, and new
measurement target kinds remain non-goals.

### 14. Save/Open Rebuilds; It Does Not Persist Derived Output

V21 introduces no document schema trigger and no `.wcad` package entry.

- V1-V22 JSON remains readable.
- Minimum-schema export remains unchanged.
- `.wcad` remains `partbench.wcad.v2`.
- Existing authoritative imported/topology checkpoint payloads remain
  preserved exactly as required by V13-V19.
- Authored-body exact artifacts and STEP bytes are never added to `.wcad`.
- After open, current exact artifacts are rebuilt from source and required
  checkpoints before export.
- JSON import that lacks required authoritative checkpoint payloads continues
  to diagnose that boundary rather than fabricating imported geometry.

No schema or package version is permitted merely for a query shape, derived
status, B-rep export artifact, writer capability, or browser job state.

### 15. Browser UX Is Explicit, Cancellable, and Accessible

The existing Project/File workspace remains the sole owner of file output.
V21 adds:

- Export all active bodies;
- Export selected body when the current semantic selection is a body;
- an explicit multi-body chooser using semantic body IDs and names;
- per-body readiness rows sourced from the shared exact-result projection;
- AP242, unit, selected-body count, and name-preservation summary;
- progress for exact artifact build and STEP write;
- Cancel and Retry actions;
- stale-result messaging with no automatic download; and
- a compact technical-details disclosure for structured diagnostics.

Apply/Cancel/Escape, focus restoration, keyboard access, narrow layout,
visible-copy, and action ownership follow V18. Export actions do not appear in
multiple workspaces. The body chooser supports keyboard-only operation and
does not require viewport picking.

The old base64 round trip is removed from the production browser execution
path. Worker `Uint8Array` bytes become a `Blob` directly after the final source
identity check. Public agent/query responses contain artifact metadata only,
not file bytes.

### 16. Agent and MCP Parity Is Readiness, Not File Authority

The existing structured adapter and MCP surface must expose:

- complete per-body exact export readiness;
- selected/all-body export plan metadata;
- source identity and plan identity;
- body names, units, schema, counts, warnings, and blockers; and
- the same stale/failed/unsupported diagnostic meanings as the browser.

Agents do not receive STEP bytes, browser handles, local paths, OPFS paths, or
an automatic Save/Download tool. V20 Manual approval and Approve everything
remain exactly the two mutation approval modes. Export planning is read-only
and creates no approval proposal. V21 adds no transport, permission mode,
filesystem capability, or hosted behavior.

The connected browser adapter injects only bounded current derived evidence
needed for truthful readiness. The in-memory adapter, which has no OCCT/browser
artifact runtime, reports source capability separately from missing derived
execution evidence rather than claiming a file is ready.

### 17. Failure and Diagnostic Semantics Are Complete

V21 retains compatible existing export diagnostics and adds the minimum set
needed to distinguish root causes. Final names may follow established naming,
but must cover:

```text
EXPORT_BODY_SELECTION_INVALID
EXPORT_BODY_DUPLICATE
EXPORT_BODY_NOT_ACTIVE
EXPORT_EXACT_SOURCE_UNAVAILABLE
EXPORT_EXACT_SOURCE_STALE
EXPORT_EXACT_ARTIFACT_FAILED
EXPORT_EXACT_ARTIFACT_INVALID
EXPORT_EXACT_ARTIFACT_LIMIT_EXCEEDED
EXPORT_SOURCE_CHANGED
EXPORT_CANCELLED
EXPORT_STEP_NAMED_WRITER_UNAVAILABLE
EXPORT_STEP_TRANSFER_FAILED
EXPORT_STEP_WRITE_FAILED
EXPORT_STEP_ARTIFACT_INVALID
```

Failures are atomic: no source mutation, history entry, checkpoint source
record, dirty-state change, partial download, or retained stale artifact.

Expected fault coverage includes missing/corrupt checkpoint payloads, hash or
length mismatch, null/empty B-rep, missing OCCT bindings, writer transfer/write
failure, duplicate/missing/consumed bodies, mixed ready/blocked selection,
source edits at every async boundary, worker disconnect/termination,
cancellation, out-of-order responses, detached buffers, and browser download
failure after valid byte creation.

### 18. Resource and Security Limits Are Explicit

V21 export work is bounded by protocol constants:

- at most 256 explicitly selected bodies per export plan;
- at most 4,096 exact source graph nodes across one plan;
- at most 128 MiB for one in-memory B-rep artifact;
- at most 512 MiB aggregate B-rep artifact bytes for one export;
- at most 512 MiB for the final STEP artifact;
- no duplicate body IDs or cyclic exact source graph; and
- all numeric geometry and metadata values must be finite.

Exceeding a limit is a blocking diagnostic before STEP transfer whenever it can
be known. The writer processes bodies in plan order and releases each parsed
shape after transfer. Cancellation guarantees no download; if synchronous OCCT
cannot yield promptly, the app may terminate and recreate the existing
geometry worker because all worker state is derived.

Input B-rep bytes are treated as untrusted binary at the worker boundary. They
are length/hash checked, parsed inside isolated OCCT/WASM, never interpreted on
the main thread, and never exposed to cad-core or MCP. Temporary WASM files use
unique bounded names and are unlinked in `finally` paths.

### 19. Performance and Bundle Budgets Remain Release Gates

V21 retains the V19/V20 critical UI, CSS, all-UI, command-worker, and
geometry-worker caps. New export UI and execution code must remain lazy. An
empty project and ordinary sketch work must not load OCCT/WASM or build exact
artifacts merely because V21 is installed.

`check:v21-bundle` enforces these inherited fixed ceilings rather than
refreshing a moving baseline:

```text
critical UI JavaScript            <= 409,600 gzip bytes (400 KiB)
critical CSS                      <= 20,480 gzip bytes (20 KiB)
all non-worker UI JavaScript      <= 563,200 gzip bytes (550 KiB)
command worker                    <= 262,144 gzip bytes (256 KiB)
geometry worker                   <= 122,880 gzip bytes (120 KiB)
OCCT WASM without new name binding <= 13,808,536 gzip bytes
OCCT WASM with required name binding <= 14,500,000 gzip bytes
```

The existing OCCT WASM gzip cap remains `13,808,536` bytes when named STEP
support requires no new binding surface. If Slice A proves required name
bindings are absent, the approved V21 ceiling is `14,500,000` gzip bytes, and
the release record must report the exact delta and symbols added. This is not
permission to add unrelated OCCT modules.

Runtime gates include:

- export interaction feedback by the next animation frame;
- no main-thread base64 encoding/decoding of STEP bytes;
- no export-related main-thread task over 50 ms in the representative browser
  workflow;
- stale or cancelled worker responses never apply;
- one exact artifact build per selected body per export attempt;
- bounded retained artifact memory after success/failure/cancel; and
- recorded p50/p95 artifact-build, STEP-write, total-export, byte-size, and
  worker-restart timings for the representative corpus.

The performance smoke enforces the fixed byte/resource limits and a
repository-owned representative model. It records larger stress models without
making hardware-specific wall-clock promises the source of correctness.

### 20. No New Production Dependency or Package

Use the existing TypeScript, browser APIs, Web Crypto, geometry worker,
OpenCascade.js, checkpoint writer, STEP writer, and test infrastructure. If
named-product STEP output requires additional generated OCCT bindings, they
remain inside the current `packages/occt-wasm` dependency/build boundary.

V21 does not add a hashing package, ZIP package, stream framework, worker pool,
generic artifact registry, export plugin system, or new workspace package.

## Public and Internal Contract Changes

### Cad Protocol

Additive public work:

- exhaustive current body export source-kind vocabulary;
- exact export plan and per-body plan entries;
- current exact-result status and diagnostics;
- selected/all-body plan semantics;
- named AP242/unit metadata;
- derived exact artifact evidence metadata without bytes; and
- additive project-health coverage for every existing body family.

Compatibility work:

- old query requests remain valid;
- old response fields remain readable;
- historical commands/diffs are unchanged;
- no query response becomes project source; and
- validators reject unknown status values, malformed identities, duplicate
  body selections, non-finite counts, and artifact-byte claims in public
  evidence.

### Cad Core

Cad-core owns:

- active/consumed body classification;
- completed support-matrix eligibility;
- deterministic body selection/order;
- body-name fallback;
- project and body source identities;
- all-or-nothing export planning;
- source/dependency/reference/repair blockers;
- public readiness/health/diagnostics; and
- agent-visible plan metadata.

Cad-core does not own:

- exact source construction requiring app checkpoint bytes;
- B-rep serialization or parsing;
- STEP transfer/write;
- browser download;
- worker scheduling/cancellation; or
- session artifact storage.

### Web App

The web app owns:

- canonical current exact-body resolution;
- app-owned checkpoint payload lookup;
- shared current exact-result projection;
- plan-to-artifact orchestration;
- pre/post source identity checks;
- progress/cancel/retry;
- direct `Uint8Array` to `Blob` download; and
- Project/File and selected-body UX.

It does not infer modeling eligibility from a mesh or successful OCCT call.

### Geometry Kernel / Worker / OCCT WASM

The geometry boundary owns:

- exact source validation;
- one exact-shape dispatcher;
- artifact B-rep/metadata/topology generation;
- B-rep length/hash verification;
- named AP242 transfer;
- units;
- temporary-file cleanup;
- transferable byte ownership; and
- structured geometry errors/capabilities.

## Normative Release Scenarios

1. **Primitive and unit matrix** — export box, cylinder, sphere, cone, and
   torus bodies across `mm`, `cm`, `m`, and `in`; verify AP242 units, names,
   body count, exact physical scale, and re-imported mass/bounds.
2. **Authored feature matrix** — export real OCCT samples covering entity,
   wire, and region extrudes; add/cut; revolve; line/arc/G1 sweep; loft; hole;
   chamfer; fillet; shell; linear/circular pattern; and mirror. Every active
   body must have matching display, metadata, topology, mass, and export state.
3. **Imported downstream part** — import a named STEP solid, preserve its
   checkpoint, perform each completed supported downstream add/cut/hole/edge
   finish path in separate deterministic samples, export the final body, and
   re-import with equivalent exact properties.
4. **Selected and multi-body output** — export one semantic selection and an
   explicit ordered set with duplicate and Unicode names; prove order, names,
   units, all-or-nothing failure, subset retry, and no renderer ID authority.
5. **Rebuild and staleness** — save/open `.wcad`, rebuild, start export, apply a
   human edit and an approved agent edit at separate async boundaries, reject
   both stale artifacts, retry, then prove undo/redo produces the corresponding
   exact outputs.
6. **Failure and recovery** — inject corrupt checkpoint bytes, missing name
   writer, artifact write failure, STEP transfer failure, cancellation, worker
   termination, and browser download failure; prove no mutation, partial file,
   retained bytes, or stale status.
7. **Bounded multi-body workload** — export the repository-owned near-limit
   body set, enforce body/graph/byte limits, record timing/memory metrics, and
   keep the UI responsive with no main-thread base64 work.

Round-trip equivalence compares body/solid counts, units, bounds, volume,
surface area, centroid, inertia, and topology counts within the existing exact
tolerances. STEP does not promise preservation of Partbench feature history,
body IDs, topology stable IDs, or editable sketches.

## Must Definition of Done

V21 is complete only when:

1. Every active healthy body in the V21 matrix resolves through one exhaustive
   current exact-body resolver.
2. Primitive, authored, imported, and completed imported-downstream body paths
   produce identity-bound exact B-rep artifacts through real OCCT.
3. Artifact B-rep, metadata, topology, signatures, and generated references
   are derived from the same exact shape and pass corruption/cleanup tests.
4. Exact STEP execution consumes artifacts rather than feature recipes.
5. Selected-body, explicit ordered multi-body, and Export-all semantics are
   deterministic and all-or-nothing, with no silent omission.
6. AP242 output preserves all supported document units and per-body names,
   including duplicate and Unicode names.
7. Every completed body family exports exact STEP; none remains deferred solely
   because an export mapper is missing.
8. Standalone imported bodies and every completed imported-body downstream
   result export and re-import with equivalent exact properties.
9. Display, project health, topology, exact metadata, mass properties,
   body-level selection/measurement, and export report the same current exact
   state for every matrix row.
10. Source identity is verified before exact work and after STEP write; stale
    results never download.
11. Cancel, retry, worker restart, source replacement, undo, redo, New, Open,
    JSON import, and `.wcad` replacement have explicit tested semantics.
12. File output is browser-owned; agent/MCP readiness contains no artifact
    bytes, handles, paths, renderer IDs, or new permission path.
13. Production browser STEP download performs no base64 encode/decode and
    releases object URLs and artifact buffers.
14. Resource, hash, corrupt-input, missing-binding, writer-failure, and
    security tests pass at every trust boundary.
15. V21 introduces no document schema, package version, authoritative artifact
    state, OPFS exact cache, workspace package, or production dependency.
16. V12-V20 completed matrices and named V19/V20 compatibility commands remain
    green.
17. All eight named V21 commands and repository-wide validation pass.
18. README, AGENTS, architecture, implementation plan, native format, package
    documentation, release evidence, and this document agree at completion.
19. The exhaustive body-source audit contains no unclassified or partially
    exposed source kind.
20. No V21 non-goal is partially exposed as supported product behavior.

No Must item may be reclassified as optional to close the release. If real
OCCT evidence contradicts a Must row, update this plan with the exact evidence
and obtain explicit approval before changing scope.

## Explicit Non-Goals

  large-assembly LOD.
- New sketch entities, splines, ellipses, general conics, 3D sketches, or new
  constraint/dimension families.
- New solid feature families, direct modeling, unrestricted booleans, or wider
  pattern/shell/edge-finish/loft/sweep command matrices.
- Datum-plane/axis/point authoring or new parameter bindings.
- IGES, DXF, SVG, STL, 3MF, drawing, PDF, or proprietary CAD output.
- Editable STEP sketches, feature-history reconstruction from STEP, or
  Partbench ID/topology-ID preservation through STEP.
- Exact subentity highlight rewrite, generated vertex picking,
  selection-buffer overhaul, section view, clipping, or persisted measurements.
- Production WebGPU, renderer authority, or mesh-based exactness.
- Persisted authored-body B-rep artifacts, STEP bytes in `.wcad`, new OPFS
  source/cache kinds, or a new package version.
- Agent file bytes, file handles, paths, automatic download, shell/network
  access, hosted MCP, collaboration, or additional approval modes.
- A generic export plugin framework, artifact registry, worker pool, stream
  protocol, new workspace package, or production dependency.

## Rejected Alternatives

1. **Add one export recipe per missing feature.** Rejected because it preserves
   the duplicated feature-to-shape dispatch that caused the gap.
2. **Export the current display mesh.** Rejected because STEP is exact B-rep
   interchange and meshes are derived visualization.
3. **Treat successful OCCT execution as command support.** Rejected because
   cad-core's completed support matrix remains authoritative.
4. **Persist every authored exact artifact in `.wcad`.** Rejected because
   source already rebuilds those artifacts and persistence would create stale
   dual authority.
5. **Use topology checkpoints as automatic source for every body.** Rejected
   because explicit checkpoints have topology authority semantics; export
   artifacts are transient.
6. **Return STEP bytes through MCP.** Rejected because V20 deliberately denies
   agent file authority and large base64 query payloads are wasteful.
7. **Skip unsupported bodies during Export all.** Rejected because silent
   omission produces incomplete manufacturing artifacts.
8. **Rename duplicate bodies automatically.** Rejected because export must not
   alter authored names silently.
9. **Keep base64 because it already works.** Rejected because it duplicates
   large buffers and blocks the main thread without adding authority or safety.
10. **Combine V21 with assemblies, direct edit, drawings, or more formats.**
    Rejected because this release establishes the exact part artifact those
    later systems should consume.

## Risk Controls

| Risk | Control |
| --- | --- |
| Exact consumers still build different shapes | One exhaustive resolver, one exact-shape dispatcher, same-shape artifact metadata/topology, differential tests |
| Internal B-rep leaf widens modeling support | Cad-core eligibility first; resolver emits only completed rows; matrix audit |
| Source changes during export | Project + body identity before and after; generation cancellation; discard stale bytes |
| Imported checkpoint is corrupt or mismatched | Manifest/body/feature/hash validation before isolated OCCT parse |
| Name-preserving bindings are unavailable | Slice A real-browser capability gate; minimal existing-package binding extension; no fallback that drops names |
| Multi-body export silently omits work | Explicit ordered all-or-nothing plan; subset requires explicit new plan |
| Large artifacts exhaust memory | Fixed body/graph/per-body/aggregate/output caps; sequential transfer; direct transferable bytes; cleanup tests |
| Main thread stalls | Lazy worker work, Web Crypto, no base64, next-frame feedback, long-task gate |
| Worker cancellation leaks state | Generation checks, terminate/recreate fallback, disposal/fault tests |
| Agent gains file authority | Metadata-only adapter projection; browser-only Blob/download; V20 security regression |
| Schema/package churn | Derived-only contract; V1-V22 and `.wcad` v2 compatibility gates |
| Release claims outrun OCCT proof | Real browser/WASM artifact, writer, re-import, and exact invariant smokes for every matrix row |
